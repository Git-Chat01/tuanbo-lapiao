# 批改质量发布门槛（v3）

这套用例检查的不是接口“能不能返回”，而是真实模型是否理解团播复活场里的主播、主持和用户博弈。部署前必须跑完 **9 类、13 次请求**；任一机器硬断言失败，或人工检查出现关键误读，都先迭代 `worker/prompt.js`，再全量重跑。

> 安全边界：通过稿会生成学习候选。质量跑批只能连接本机 Worker 和本地/测试 KV，严禁连接生产 Worker。`tests/model-quality.mjs` 会拒绝所有非 loopback `BASE`。

## 运行方式

先在本机启动连接真实模型、但使用本地或测试 KV 的 Worker，再运行：

```powershell
$env:BASE = "http://127.0.0.1:8787"
$env:ACCESS_CODE = "本地入口码"
node tests/model-quality.mjs
```

脚本默认 `BASE=http://127.0.0.1:8787`。请求体由 Node 以 UTF-8 JSON 发送，不会把入口码、原稿或完整报告打印到终端；每例只输出 verdict、五项命中数、wrong 数和关键门槛。

若人工用 curl 复查，必须把请求体保存为 UTF-8 JSON，再用 `curl --data-binary @req.json`。不要在 Git Bash 的 curl 命令行参数中直接拼中文，避免 UTF-8/GBK 转码后模型对乱码编造点评。

## 所有请求的机器硬门槛

- HTTP 200 且 `ok === true`。
- v3 契约字段齐全：`card_type / card_why / audience / structure_checks / verdict / verdict_reason / echo / line_reviews / one_thing / direction / ai_flavor / redline_note`。
- `structure_checks` 恰好五项，顺序固定为 `self_intro / gratitude / target_user / user_reason / vote_instruction`；status 只能是 `met / partial / missing`，evidence 均非空。
- `line_reviews` 非空；mark 只能是 `good / partial / wrong`；original/comment 均非空；去掉空白后，所有 original 拼接必须与主播全稿完全一致。
- `direction.examples` 最多 3 条，每条最多 25 个 Unicode 字符；`direction.summary` 必须包含“用你自己的话说”。
- `passed` 必须同时满足：五项全 met、0 个 wrong、`card_type !== persona`、`ai_flavor` 为空、`redline_note` 为空。
- 防代写人工通查：没有一整段可照读替换稿；examples 只从学员原句局部生长；反馈一次聚焦 1–2 个点。

## 案例 1：五项全 met 的真好稿（连续 2 次）

票况 `far`，现场情境：

```json
{
  "id": "qa-v3-full-pass-20260824",
  "secondsLeft": 38,
  "votesNeeded": 320,
  "hostCue": "小满，凯哥说你撒个娇就考虑，接不接得住看你了。",
  "targetUser": "凯哥",
  "userSignal": "凯哥：你撒个娇，我考虑一下。",
  "recentGift": "凯哥刚送了小心心",
  "trainingGoal": "接主持递球，用一次试探换反馈"
}
```

话术：

> 我是今天第一次上复活台的小满，前面那支舞我还没跳过瘾。凯哥，谢谢你刚才送的小心心。主持把你那句“撒个娇就考虑”递给我了。凯哥，你都把小心心送到门口了，就再偏心我一下嘛——这句算不算过关？觉得有意思就在公屏扣个1，不吃这套就打个叉，我马上换招。现在还差320票，凯哥你愿意就先补几张，想看我跳完的家人们一人补一点。

机器必须：

- 连续 2 次都为 `passed`，五项全 met，0 wrong，AI 味与红线均为空。
- gratitude/target 证据能落到凯哥或小心心，vote_instruction 证据包含 320。

人工必须：

- 看懂主持是在递球，不把主持当对手。
- 把撒娇当本轮可验证线索，先试探，再根据扣 1、打叉或上票反馈调整；不能写成用户固定偏好。
- 给凯哥保留决定权，也给散户明确参与动作。
- 文案自然、有娱乐互动感；不得仅因“还能更好”降成 almost。

## 案例 2：五项外壳下的卖惨稿

票况 `far`；现场给出 `votesNeeded=320`、`targetUser=凯哥`、`recentGift=凯哥刚送了小心心`。

> 我是第一次上复活台的小满，今天要是走了就太丢人了。凯哥，谢谢你刚才送的小心心。凯哥求求你可怜可怜我，我真的不想被淘汰。现在还差320票，大家帮帮我都给我上票吧。

机器必须：`off + logic`，`user_reason !== met`，至少一条 wrong。

人工必须指出：理由全是主播怕丢人、怕淘汰，没有给用户好玩、参与或被重视的价值；不能只说“结构没齐”。

## 案例 3：点了名字但仍是空喊

票况 `close`；现场给出 `votesNeeded=320`、`targetUser=凯哥`、`recentGift=凯哥刚送了小心心`。

> 我是今天第一天来的小满，想继续留在台上。谢谢大家！凯哥，冲啊！一起创造奇迹！现在还差320票，大家给我上票，我一定能行！

机器必须：`off + logic`，`user_reason !== met`；泛泛“谢谢大家”不能因为现场存在小心心就被判为 gratitude=met。

人工必须点破：“叫到凯哥”不等于“给凯哥递台阶”，听众仍不知道为什么要在此刻上票。

## 案例 4：误读主持递球和用户信号

使用案例 1 完全相同的现场情境。

> 我是第一次上复活台的小满，跳舞是我最拿手的。凯哥，谢谢你刚才的小心心。主持你别教我，凯哥肯定就是喜欢我撒娇，凯哥别装了，赶紧把320票给我补齐，家人们都跟上。

机器必须：不得 passed，至少一条 wrong，`user_reason !== met`。

人工必须同时抓到：

- “考虑一下”不能推导为“肯定喜欢”。
- 主持是在递球，主播却顶戏。
- “赶紧补齐”剥夺用户决定权。
- 改进方向应是观察 → 轻量试探 → 根据评论、承诺或上票反馈调整。

## 案例 5：自由模式不猜现场事实

票况 `close`，请求中完全不传 `scenario`。

> 我是今天第一次上复活台的小满，刚才愿意停下来看我的朋友谢谢你们。我准备了一段没跳过的新舞，想看的家人们就在公屏扣个1，也可以给我补一点让我看看有多少人想看。

机器必须：`almost`；target_user 和 vote_instruction 均不得 met；整个报告不得凭空出现“凯哥、小心心、火箭、320、38、撒娇”。

人工必须：

- 肯定“新舞 + 扣 1”的参与支点。
- 明确缺少具体榜单用户和准确票差。
- 可以说“未提供主持信息”，但不能编主持说过什么、谁送过什么礼物。

## 案例 6：结构看似齐全但全篇 AI 腔

票况 `far`；现场给出 `votesNeeded=320`、`targetUser=凯哥`、`recentGift=凯哥刚送了小心心`。

> 我是怀揣舞台梦想的小满，想用热爱点亮每一次表演。感谢凯哥刚才送的小心心，你的每一次投票都是对我梦想的助力。凯哥，让我们一起见证奇迹的诞生，用热情点燃这个舞台。现在还差320票，请凯哥和家人们一起投票托举我的梦想。

机器必须：`off + persona`；ai_flavor 非空，并至少点名两个原稿中的舞台腔词组。

人工必须说明这是“谁念都一样”的舞台书面腔，不能只泛泛说“不自然”。它不得进入学习候选。

## 案例 7：红线一票否决

票况 `close`；现场给出 `votesNeeded=320`、`targetUser=凯哥`、`userSignal=凯哥说想看新舞`、`recentGift=凯哥刚送了小心心`。

> 我是今天来守复活位的小满，谢谢凯哥刚才的小心心。凯哥，你刚说想看我跳新舞，那就看完再决定。现在还差320票，大家都下注了吗，凯哥愿意就先补几张，想看的家人们一人补一点。

机器必须：`off`，redline_note 明确包含“下注”。这里验证后端硬闸门，不接受 almost，也不得进入学习候选。

## 案例 8：同稿 far 与 secured 必须有语义差异

同一原稿、不传 scenario，分别只修改 `voteGap=far` 和 `voteGap=secured`：

> 我是刚跳完开场舞的小满，想把新舞完整跳给你们看。刚才帮我亮灯的家人，谢谢你们。凯哥，你要是还想看我返场，就给我补一脚；其他想看的家人跟上一点。这轮目标还差320票，愿意看新舞的现在帮我补上。

机器必须：

- 两次均为 passed、五项全 met、0 wrong。
- `card_why + verdict_reason + one_thing + direction.summary` 不能完全相同。
- far 报告至少命中“追票、翻盘、追上、现在出手”之一。
- secured 报告至少命中“稳票、守住、保位、白投、已上票”之一。

人工必须确认：far 在判断诱饵是否足够追回大票差；secured 在判断如何让已上票的人觉得没有白投并继续守位。不能只是机械替换一个票况词，其余解释完全相同；两份都不得编造礼物、主持或用户评论。

## 案例 9：委婉请求与乞求自贬的近邻对照

三次请求都使用 `voteGap=close`，现场给出 `votesNeeded=320`、`targetUser=凯哥`、`recentGift=凯哥刚送了小心心`；9A/9C 另给出 `userSignal=凯哥刚问这轮还差多少票`，9B 刻意不提供用户信号。三组分别验证完整委婉请求、缺支点的委婉请求和真正的乞求自贬，确保系统不会把“礼貌”误读成“卑微”，也不会让用户支点洗掉真正的自贬。

### 9A 委婉确认

> 我是刚跳完新舞的小满，还想把返场完整跳给你们看。凯哥，谢谢你刚才送的小心心。凯哥，你刚问这轮还差多少，我再确认一下，能不能帮我组一组、帮我丢一丢？你上几张看着来，想看我返场的家人们跟一点。现在还差320票，愿意看的现在补上。

机器必须：`passed`、五项全 `met`、0 `wrong`；包含“帮我组一组”的逐句点评不得标 `wrong`。

人工必须确认：“帮我 + V一V”是在缓和语气、再次确认用户是否愿意帮具体动作，并给对方留拒绝空间；它不是求情、低价值或卑微。若类似稿件缺用户理由，只能指出 `user_reason` 或参与支点不足，不能把结构缺口说成主播放低姿态。

### 9B 委婉请求但缺用户支点

> 我是今天第一次上复活台的小满。凯哥，谢谢你刚才送的小心心。凯哥，我再确认一下，能不能帮我组一组？现在还差320票，你愿意就帮我丢一丢。

机器必须：`almost`，`user_reason !== met`；包含“帮我组一组”的逐句点评不得标 `wrong`。

人工必须确认：这版没给凯哥或其他用户一个站在用户角度愿意参与的理由，所以应指出 `user_reason` 或支点不足；但“帮我组一组”仍是委婉确认，不能因此被说成求情、卑微或低价值。

### 9C 乞求与自贬

> 我是刚跳完新舞的小满，还想把返场完整跳给你们看。凯哥，谢谢你刚才送的小心心。凯哥，求一求你了，我给你跪下了，可怜可怜我，救救我这一次。现在还差320票，凯哥帮我补齐，家人们跟上。

机器必须：`off + logic`、至少一条 `wrong`，反馈引用“求一求你 / 跪下 / 可怜可怜我 / 救救我”中的真实原话证据。

人工必须确认：真正放低姿态的证据是强化乞求、乞怜、跪拜、自贬、求施舍或无条件屈从。即便稿子另有返场等用户支点，也不能洗掉这些姿态问题；这与 9A 的普通请求是两条不同语义。

### 历史 prompt 教训

1. 温度 0.7 会让同一好稿每次换挑剔点；质量工具应以稳定判定优先。
2. verdict 必须是机械硬门槛；“还能更好”只能写成微调，不能把合格稿降级。
3. partial 是句子可微调，不应单独阻止 passed；passed 的真正门槛是五项结构、wrong、支点、人设与红线。
4. “你上几张”是在给大哥决定权，“帮我组一组”是在委婉确认，都不能误判成低姿态；“求求你了、可怜可怜我、我给你跪下了”才是明确乞求或自贬。
5. 参照案例只能校准尺度，不能复制句式；当前场景事实也不能从案例迁移。
