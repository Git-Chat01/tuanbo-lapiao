# 浏览器批改任务恢复

新版页面使用 `POST /api/coach/jobs` 提交，再用 `POST /api/coach/jobs/:uuid` 查询。两者都在 JSON 正文携带入口码，查询响应禁用缓存。旧 `POST /api/coach` 继续兼容旧页面和脚本。

浏览器在发请求前生成随机 UUID 并保存任务指针。收到创建回包前断网，再次发送同一 UUID；收到后只查询。刷新会恢复尚在等待的工作区；主动返回编辑后不自动抢回页面。同一任务的原稿、背景、改稿回执不可变，内容变化必须新建任务。不同标签页只保留最近一次提交的恢复指针，旧页继续查询自己的任务但不能覆盖新指针。

`COACH_JOBS` 每个对象对应一个入口码作用域内的 UUID。SQLite 事务同时保存原稿与 alarm，由 alarm 执行原有批改流程。浏览器连接断开不控制其生命周期。创建回包丢失或重复轮询不重复调用模型；任务开始时只计一次限流，沿用原入口码/IP 桶。入口码、API 密钥和原始 IP 不写入任务存储。

任务结果保留 24 小时；成功报告仍保留 7 天不可变回执以供复练。执行结束即移除任务中的原稿及 IP 指纹。原模型仍使用 90 秒生成/修正预算，后台整条任务最多等待 150 秒；浏览器单次查询最多 12 秒，前台连续等待最多 180 秒。前台超时后保留指针，人工重连继续查原任务。模型确实失败时显示明确错误，下一次人工重试新建任务。

Alarms 是至少一次执行。若平台在模型执行期间重启，无法证明上游是否已计费，恢复时会把该任务标为中断，不盲目自动再生成。结果持久化失败同样不会被误报成功。不能承诺平台故障下模型调用恰好一次或每次都有成功结果。浏览器禁用本地存储时只能在当前页面保留指针，界面会提示保留页面；换设备或清除站点数据不能自动找回任务。

## 耗时依据与优化边界

本地既有真实模型样本 `novice-coaching-live-baseline-timing.json` 中，4 次首批为 23.355、30.918、44.162、27.824 秒，3 次复批为 17.653、25.821、31.164 秒。对应模型原始响应记录表明首批模型以外的开销均不超过 82 毫秒；44.162 秒那次包含一次 7.567 秒的报告修正。这是有限的虚构样本，不能当作线上平均值或高峰 SLA。

此前快速候选的 14 个样本只有 2 个通过整条质量断言，不能用其速度收益交换批改准确性。本轮保留模型、完整提示词、推理配置和评分版本，优化的是重复等待与重复生成。新增日志只记录元信息：

- `coach_job`：排队、执行耗时及结束状态。
- `coach_model_timing`：每次初批/报告修正的响应头、正文耗时、缓存/推理/输出 token；响应头时间不是首 token 时间。
- `coach_timing`：准备、评审、回执保存及总耗时，是否实际启动模型。复用也可能是在等待共享中的生成，不能只凭 `generated:false` 就断定为瞬时缓存命中。

日志不记录原稿、模型正文或入口码。后续速度试验应同时比较耗时与完整教学断言，不能只统计 HTTP 200。

## 验证与发布

`node tests/coach-jobs-safety.mjs` 与 `node tests/coach-jobs-client.mjs` 无网络验证创建幂等、鉴权、配额、重启/过期、断网/刷新/取消/超时和报告恢复。`node tests/coach-jobs-runtime.mjs` 使用已安装的 Miniflare/workerd，验证实际 SQLite 事务与 alarm，使用本地缓存样本，不调用外部模型。

发布顺序：先部署 `wrangler.jsonc` 的 `COACH_JOBS` 绑定和 `coach-jobs-v1` SQLite migration，再检查健康接口 `serviceVersion=2026-10-05-durable-jobs-1`，最后发布前端。新页面需要新接口，不能先上线页面。旧接口不移除，因此后端先更新不影响现有页面。后续回滚应保留新 DO 类及绑定，避免遗留任务失去读取入口。

平台语义参考：[Durable Object Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)、[SQLite storage transactions](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)。
